# Состояние

**Категория:** Поведенческие

## Какую проблему решает

Объект ведёт себя очень по-разному в зависимости от текущего состояния, и каждый метод содержит сложные `if/elsif` или `switch`, проверяющие состояние. Добавление нового состояния = правки в каждом методе.

## Когда использовать

- Жизненный цикл заказа: `new -> paid -> shipped -> delivered -> returned` — каждое состояние допускает свои операции и переходы
- Рабочий процесс документа: `draft -> review -> published -> archived` — публикация черновика отличается от переопубликации
- Платёжная обработка: `pending -> authorized -> captured -> refunded` — свои допустимые переходы и поведение
- WebSocket или TCP соединение: `connecting -> open -> closing -> closed`
- Светофор: `red -> green -> yellow -> red` — каждый цвет знает, что следует за ним

## Что вы получаете

- Поведение каждого состояния инкапсулировано в объекте-состоянии — никаких гигантских switch
- Недопустимые переходы предотвращаются естественно: вызов `ship()` в `NewState` — no-op или исключение
- Новое состояние = новый класс, без правок switch в каждом методе

## Практические примеры

**Сущность заказа:** `$order->ship()` в `PaidState` переходит в `ShippedState`. Тот же вызов в `NewState` вызывает ошибку — недопустимый переход обрабатывается состоянием, не вызывающим кодом.

**Документ:** `$doc->publish()` в `DraftState` публикует. В `ArchivedState` — "нельзя переопубликовать архивный документ". Каждый класс-состояние обрабатывает по-своему.

**Пул соединений:** `idle -> borrowing -> in-use -> returning -> idle` — каждое состояние знает, какие операции допустимы.

## Признаки того, что паттерн нужен

- В каждом методе сущности есть `if $status eq "paid" { ... } elsif $status eq "shipped" { ... }` — эта логика принадлежит классам-состояниям
- Допустимые переходы хранятся в отдельном хеше `%VALID_TRANSITIONS` — это конечный автомат, пытающийся выйти наружу
