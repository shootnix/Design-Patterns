# Посредник

**Категория:** Поведенческие

## Какую проблему решает

Многие объекты взаимодействуют сложным образом, создавая жёстко связанную сеть прямых зависимостей. Добавление нового компонента требует обновления многих существующих. Посредник централизует коммуникацию — компоненты знают только посредника, не друг друга.

## Когда использовать

- Чат или WebSocket-комната: пользователи отправляют сообщения через центральный объект-комнату, никогда напрямую друг другу
- UI-форма со взаимозависимостями: смена "страны" обновляет варианты "области", но поля не должны знать друг о друге
- Event bus в микросервисах: сервисы публикуют события на шину; другие подписываются без прямых вызовов сервис-к-сервису
- ORM Unit of Work: репозитории регистрируют изменения у центрального координатора, управляющего транзакцией
- Диспетчерская вышка аэропорта: самолёты общаются через вышку, не напрямую

## Что вы получаете

- Компоненты отвязаны друг от друга — каждый знает только посредника
- Добавление нового компонента = добавление его к посреднику, не обновление каждого существующего
- Вся логика взаимодействия централизована — проще понять, протестировать и изменить

## Практические примеры

**Event bus:** `EventBus->publish("user.registered", $payload)`. `EmailService`, `AnalyticsService` и `AuditService` подписываются независимо. Никто не знает о других.

**Чат-комната:** `ChatRoom` получает сообщение от Алисы и рассылает всем остальным. Пользователи не хранят ссылок друг на друга.

**ORM Unit of Work:** `UnitOfWork` собирает вставки, обновления и удаления от всех репозиториев и выполняет их в правильном порядке внутри одной транзакции.

## Признаки того, что паттерн нужен

- N компонентов, каждый из которых вызывает методы M других — N×M зависимостей вместо N+M
- Добавление новой функции требует обновления многих существующих классов для добавления новых взаимодействий
- Код обработки событий разбросан по каждому компоненту, который их отправляет или получает

## Run

```
perl -Ilib main.pl
```
