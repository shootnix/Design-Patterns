# Мост

**Категория:** Структурные

## Какую проблему решает

Есть две независимые оси изменений, и наивное использование наследования создаёт комбинаторный взрыв подклассов: N фигур × M рендереров = N×M подклассов без Моста, N+M — с ним.

## Когда использовать

- Уведомления × каналы доставки: срочные/дайджест × email/SMS/push — 2×3=6 подклассов без Моста, 2+3=5 с ним
- Отчёты × форматы вывода: инвойс/сводка × CSV/JSON/HTML — любой тип с любым форматом, составляемые в рантайме
- Запросы к БД × тип соединения: read/write запросы × primary/replica соединения
- UI-темы × платформы: dark/light × web/iOS/Android

## Что вы получаете

- Две независимые иерархии; новая фигура не затрагивает рендереры и наоборот
- Компоновка в рантайме: любой рендерер передаётся любой фигуре в конструктор
- Нет взрыва классов: три фигуры + четыре рендерера = 7 классов, не 12

## Практические примеры

**Уведомления:** `UrgentNotification` и `DigestNotification` хранят `DeliveryChannel`. Комбинация: `UrgentNotification(channel: SMS)` без создания `UrgentSMSNotification`.

**Рендеринг:** `Circle` и `Rectangle` хранят `Renderer` (Vector или Raster). Любая фигура × любой рендерер без N×M подклассов.

**ORM-соединения:** `ReadQuery` и `WriteQuery` хранят `Connection` (primary или replica). Смена соединения не затрагивает логику запроса.

## Признаки того, что паттерн нужен

- Есть классы типа `EmailUrgentNotification`, `SMSUrgentNotification` и вы собираетесь добавить `DigestNotification` варианты
- Добавляете `if format == "csv" ... else if format == "json"` внутри нескольких несвязанных классов
