# Цепочка обязанностей

**Категория:** Поведенческие

## Какую проблему решает

Несколько обработчиков могут обработать запрос, но кто именно — неизвестно заранее. Отправитель должен быть отвязан от всех потенциальных обработчиков, и каждый обработчик сам решает — обработать или передать дальше.

## Когда использовать

- Конвейер HTTP-middleware: каждый middleware либо обрабатывает запрос (ранний возврат при ошибке auth), либо передаёт следующему
- Конвейер валидации: проверка обязательных полей → проверка формата → бизнес-правила — остановка на первой ошибке
- Согласование покупок: тимлид одобряет до $100, менеджер до $1000, директор до $10000, VP — остальное
- Обработка ошибок: специфичные обработчики имеют приоритет; универсальный catch-all стоит последним
- Всплытие событий: событие клика передаётся вверх по UI-компонентам, пока один не обработает его

## Что вы получаете

- Отправитель не знает, какой обработчик обработает запрос
- Обработчики отвязаны друг от друга — каждый знает только о своём преемнике
- Цепочку можно переконфигурировать или расширить в рантайме

## Практические примеры

**Middleware:** `Auth -> RateLimit -> Validate -> Handle`. Любой middleware может прервать цепочку, вернув ответ без вызова `next()`.

**Согласование покупок:** `TeamLead($50) -> pass -> Manager($500) -> pass -> Director($5000) -> pass -> VP($50000 одобрен)`.

**Валидация ввода:** `RequiredCheck -> TypeCheck -> LengthCheck -> BusinessRuleCheck`. Каждый возвращает ошибку или вызывает следующий.

## Признаки того, что паттерн нужен

- Есть длинная цепочка `if/else if`, решающая какой обработчик обрабатывает запрос — эти ветки принадлежат отдельным классам
- Хочется добавлять, удалять или переупорядочивать шаги обработки без изменения самих обработчиков
