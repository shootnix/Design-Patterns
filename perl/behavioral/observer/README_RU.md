# Наблюдатель

**Категория:** Поведенческие

## Какую проблему решает

Когда один объект меняет состояние, другие должны реагировать автоматически — но изменившийся объект не должен знать обо всех своих зависимых. Жёсткое кодирование этих реакций связывает отправителя с каждым получателем.

## Когда использовать

- Хуки жизненного цикла ORM: после сохранения пользователя должен инвалидироваться кеш, обновиться поисковый индекс, записаться в журнал аудита — без знания логики сохранения об этих сервисах
- Событийная архитектура: событие `order.placed` вызывает email-уведомление, обновление склада и аналитику — каждый как независимый подписчик
- Реалтайм UI: при изменении записи в БД — push-обновление всем подключённым WebSocket-клиентам
- Горячая перезагрузка конфига: при изменении файла конфига все компоненты с ссылкой на него обновляют настройки

## Что вы получаете

- Subject отправляет событие; он не знает, кто слушает
- Наблюдатели добавляются и удаляются в рантайме без изменения субъекта
- Одно событие вызывает несколько независимых реакций — каждый наблюдатель отвечает за своё

## Практические примеры

**Хуки ORM:** `User.afterSave($user)` уведомляет `CacheService`, `SearchIndexer` и `AuditLogger`. Каждый подписан независимо; новый подписчик добавляется без правок логики сохранения.

**Котировки акций:** `StockMarket->set_price("AAPL", 185)` одновременно уведомляет всех подписанных `Investor` и `PriceMonitor`.

**WebSocket-трансляция:** При изменении статуса заказа в БД все клиенты, просматривающие этот заказ, получают push-обновление — сервис заказов просто отправляет `order.updated`.

## Признаки того, что паттерн нужен

- Каждый раз при сохранении сущности вызываются `email_service->send()`, `analytics->track()`, `cache->invalidate()` — эти вызовы должны быть наблюдателями
- Добавление новой реакции на событие требует изменения кода, который это событие отправляет
