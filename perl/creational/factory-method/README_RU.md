# Фабричный метод

**Категория:** Порождающие

## Какую проблему решает

Базовый класс или фреймворк должен создавать объекты, но конкретный тип зависит от подкласса или контекста. Хочется избежать жёсткой привязки к конкретному типу в базовом классе.

## Когда использовать

- Базовый `Controller` фреймворка создаёт объекты-ответы, но каждый подкласс должен порождать свой тип
- Каждый тип репозитория создаёт свой объект запроса с типобезопасными скоупами
- Плагинная система, где каждый плагин регистрирует свой создатель, а фреймворк вызывает их единообразно
- Выбор транспорта: конкретный тип зависит от подкласса логистики

## Что вы получаете

- Базовый класс определяет контракт создания; подклассы решают, что именно создавать
- Новый тип = новый подкласс только — никаких изменений в базовом классе
- Алгоритм, использующий созданный объект, живёт в одном месте

## Практические примеры

**Веб-фреймворк:** Базовый `Controller` определяет `create_response()`. `APIController` возвращает `JSONResponse`, `HTMLController` — `ViewResponse`. Логика `handle()` одна для обоих.

**ORM-репозиторий:** Базовый `Repository` определяет `create_query()`. `UserRepository` возвращает объект запроса со встроенными скоупами `active()`, `with_role()`.

**Логистика:** `RoadLogistics->create_transport()` возвращает `Truck`; `SeaLogistics->create_transport()` — `Ship`. `plan_delivery()` одинаков для обоих.

## Признаки того, что паттерн нужен

- Базовый класс вызывает `MyConcreteClass->new()` напрямую — подклассы не могут переопределить создаваемый тип
- Вы пишете код фреймворка/библиотеки и хотите дать пользователям возможность инжектировать конкретный тип

## Запуск

```
perl main.pl
```
