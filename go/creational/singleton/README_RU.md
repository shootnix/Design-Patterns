# Одиночка

**Категория:** Порождающие

## Какую проблему решает

Некоторые ресурсы должны иметь ровно один экземпляр на всё приложение. Создание нескольких экземпляров вызывает баги: дублирование соединений, конфликт конфигураций, раздробленный кэш.

## Когда использовать

- Пул соединений с БД — один пул на процесс, разделяемый всеми горутинами/потоками
- Конфиг приложения — загружается один раз при старте, читается везде без повторного парсинга
- Логгер — единственный экземпляр направляет все записи в одно место
- In-memory кэш (например, кэш результатов запросов) — должен быть общим; два экземпляра = два кэша, не видящих данные друг друга

## Что вы получаете

- Гарантированно один экземпляр с глобальной точкой доступа
- Ленивая инициализация — создаётся только при первом обращении
- Потокобезопасная инициализация через `sync.Once` в Go

## Практические примеры

**Пул БД:** `db.GetPool()` везде возвращает один `*sql.DB`. Два пула расходуют соединения вдвойне и упираются в лимит БД.

**Логгер:** `logger.GetInstance().Info("request received")` всегда направляет записи в один файл/сервис, какой бы пакет ни вызывал.

**Фичефлаги:** `FeatureFlags.GetInstance()` загружает флаги один раз из конфиг-сервиса и отдаёт все запросы из памяти.

## Признаки того, что паттерн нужен

- Вы передаёте один и тот же объект через 5 слоёв конструкторов только ради того, чтобы им поделиться
- Вы случайно создали два пула соединений и упёрлись в лимит БД
- Хотите гарантировать инициализацию ресурса ровно один раз при старте, сколько бы пакетов его ни импортировало
