# Прототип

**Категория:** Порождающие

## Какую проблему решает

Инициализация объекта дорогостоящая (запрос в БД, сложная настройка, сетевой вызов), или нужно много почти идентичных объектов с небольшими вариациями. Пересоздавать каждый раз с нуля расточительно.

## Когда использовать

- Клонировать базовый объект запроса для получения вариантов с разными WHERE, сохраняя одинаковые JOIN и eager-загрузки
- Загрузить тяжёлый конфиг или шаблон один раз, затем клонировать и переопределять значения для каждого клиента или запроса
- Предварительно настроить сложные объекты (HTTP-клиенты, форматтеры, валидаторы) и клонировать их для каждого сценария
- Реализовать copy-on-write: разделять состояние до момента мутации, затем клонировать

## Что вы получаете

- Новые объекты создаются копированием существующего — без повторной дорогостоящей инициализации
- Клоны полностью независимы — мутация одного не затрагивает оригинал и другие клоны
- Реестр прототипов работает как именованная фабрика объектов без знания конкретного класса

## Практические примеры

**Объекты запросов:** `baseQuery.Clone()` → добавить `.Where("status = 'active'")` на один клон, `.Where("status = 'pending'")` на другой. Оба разделяют JOIN и пагинацию.

**Конфиг на клиента:** Загружаете production-конфиг один раз. На каждый запрос: `cfg := masterConfig.Clone(); cfg.SetTenantID(id)`. Никаких повторных чтений файлов.

**Envelope API-ответа:** Предварительно собранный шаблон ответа клонируется на каждый запрос и заполняется данными — не надо каждый раз пересобирать метаданные.

## Признаки того, что паттерн нужен

- Вы вызываете `new MyObject(param1, param2, ...)` многократно с почти одинаковыми значениями, меняя только одно-два поля
- Инициализация объекта медленная и происходит в горячем пути (каждый запрос, каждая итерация цикла)
- Хотите «шаблон» объекта, который пользователи копируют и настраивают, не трогая оригинал
