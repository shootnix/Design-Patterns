# Фабричный метод

**Категория:** Порождающие

## Какую проблему решает

Базовый класс или фреймворк должен создавать объекты, но конкретный тип зависит от подкласса или контекста. Хочется избежать жёсткой привязки к конкретному типу в базовом классе.

## Когда использовать

- Базовый `Controller` фреймворка создаёт объекты-ответы, но каждый подкласс (`APIController`, `HTMLController`) должен порождать свой тип ответа
- Каждый тип репозитория создаёт свой объект запроса с типобезопасными скоупами и eager-загрузками
- Плагинная система, где каждый плагин регистрирует свой создатель, а фреймворк вызывает их единообразно
- Выбор транспорта: какой конкретный транспорт создать зависит от подкласса логистики

## Что вы получаете

- Базовый класс определяет контракт создания; подклассы решают, что именно создавать
- Новый тип = новый подкласс только — никаких изменений в базовом классе
- Алгоритм, который *использует* созданный объект, живёт в одном месте

## Практические примеры

**Веб-фреймворк:** Базовый `Controller` определяет фабричный метод `createResponse()`. `APIController` возвращает `JSONResponse`, `HTMLController` — `ViewResponse`. Логика `handle()` одна для обоих.

**ORM-репозиторий:** Базовый `Repository` определяет `createQuery()`. `UserRepository` возвращает `UserQuery` со встроенными скоупами `.active()` и `.withRole()`.

**Логистика:** `RoadLogistics.createTransport()` возвращает `Truck`; `SeaLogistics.createTransport()` — `Ship`. `planDelivery()` одинаков для обоих.

## Признаки того, что паттерн нужен

- Базовый класс вызывает `new ConcreteClass()` напрямую — подклассы не могут переопределить создаваемый тип
- Вы пишете код фреймворка/библиотеки и хотите дать пользователям возможность инжектировать конкретный тип

## Запуск

```
go run .
```
