# Фасад

**Категория:** Структурные

## Какую проблему решает

Клиентский код должен оркестрировать множество подсистем для выполнения одной операции, создавая жёсткую связность и дублируя логику координации везде, где она нужна.

## Когда использовать

- Регистрация пользователя: проверка + хеширование пароля + запись в БД + отправка письма + аналитика — пять сервисов, одна операция
- Оформление заказа: проверка склада + списание карты + создание отправления — три сервиса, один метод фасада
- ORM-миграции: инспекция схемы + вычисление diff + генерация SQL + выполнение в транзакции + откат при ошибке
- API-шлюз, агрегирующий данные нескольких микросервисов перед ответом

## Что вы получаете

- Один вызов метода делает всё что нужно — у вызывающего одна зависимость вместо пяти
- Логика координации живёт в одном месте — меняете последовательность раз, все вызывающие получают изменение
- Подсистемы могут развиваться внутри без поломки клиентов

## Практические примеры

**UserService->register($email, $password):** Внутри вызывает `Validator`, `Hasher`, `UserRepository`, `Mailer`, `Analytics`. Вызывающий ничего об этом не знает.

**OrderFacade->place_order($item, $qty, $card):** Вызывает `InventoryService`, `PaymentService`, `ShippingService` последовательно с обработкой ошибок.

**MigrationRunner->run():** Сравнивает схемы, генерирует SQL, выполняет в транзакции. Вызывающий просто вызывает `run()`.

## Признаки того, что паттерн нужен

- Контроллеры импортируют 5+ сервисов и вызывают их в одной и той же последовательности — эта последовательность должна жить в одном месте
- Копируете одну и ту же логику оркестрации "вызов A, затем B, затем C" в нескольких местах
