# Заместитель

**Категория:** Структурные

## Какую проблему решает

Нужно контролировать доступ к объекту — добавить ленивую загрузку, кеширование, контроль доступа или логирование — не изменяя ни реальный объект, ни клиентский код.

## Когда использовать

- **Ленивая загрузка:** связи ORM загружаются только при обращении (`$user->posts` выполняет запрос при первом доступе, не при загрузке `$user`)
- **Кеширование:** API-клиент, возвращающий кешированные ответы; обращается к реальному сервису только при промахе
- **Контроль доступа:** проверка прав перед делегированием репозиторию (`может ли пользователь читать эту сущность?`)
- **Логирование:** прозрачное логирование каждого вызова метода без изменения реального объекта
- **Удалённый заместитель:** сетевой сервис выглядит как локальный объект

## Что вы получаете

- Клиент использует заместителя точно так же, как реальный объект — тот же интерфейс, никаких изменений в вызывающем коде
- Реальный объект создаётся или загружается только когда действительно нужен
- Сквозные задачи (кеш, авторизация, логирование) остаются вне бизнес-логики

## Практические примеры

**Ленивая загрузка ORM:** `$user->posts` возвращает заместителя; SQL `SELECT * FROM posts WHERE user_id = ?` выполняется только при итерации — предотвращает жадную загрузку всех связей.

**Кешируемый HTTP-клиент:** `CachingClient->get("/api/users/1")` сначала проверяет Redis; обращается к реальному HTTP-клиенту только при промахе.

**Заместитель с правами:** `SecureRepository->find_by_id($id)` проверяет `$user->can("read", $entity)` перед вызовом реального репозитория. Права живут в одном месте.

## Признаки того, что паттерн нужен

- Загружаете все связанные данные жадно "на всякий случай" и это вызывает медленные запросы — ленивая загрузка через заместителя решит это
- Перед каждым вызовом сервиса есть `if ($cache->has($key)) { return $cache->get($key); }` — эта логика принадлежит заместителю
- Проверки прав происходят внутри методов репозитория — они принадлежат отдельному заместителю контроля доступа
